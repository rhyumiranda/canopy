The Orchestration Layer

A supervisor sitting one level above your workers. It holds the plan, spins up isolated work, has an independent agent grade the result, and only taps you on the shoulder when a real decision needs a human.

The pain

One project, many Claude windows. You lose track of what each session did. Constant context-switching. Most of your energy goes to managing agents, not to the work. Windows drift, threads tangle, things get mixed up.

The fix

Add a layer whose only job is to run the other agents. It never edits code itself — it delegates, isolates, verifies, and reports. You steer from one seat and can drop into any worker window when one goes off-plan.

Intent → isolated build → independent review → gate → tests → lint → PR → merge → teardown. The review↔fix cycle never exits until the reviewer says it is clean.

Who does what

1 Orchestrator Claude Code

This very Claude Code session — your seat. Delegates via subagents, never edits code itself. The only place decisions come back to. Clearing it must not lose work — that is why .canopy/ exists.

2 .canopy/ — brief + state

brief.md captures intent up front; state.json tracks the live task board. Together they are the memory — wipe the orchestrator and the plan survives on disk. Name = your call, see below.

3 treehouse pool

treehouse leases a worktree from a reusable pool — one branch per task, no collisions. On merge it returns to the pool, keeping deps & build cache (not destroyed).

4 Worker subagent

Lives in the worktree and does the actual implementation. Fixes bugs it hits along the way. Re-invoked whenever the reviewer or a gate sends work back.

5 Ephemeral diff reviewer

A fresh agent that sees only the git diff — not the worker's chat. Being independent is the whole point: a worker reviewing itself is an echo chamber.

6 Merge watcher

One background job watches all open PRs (poll or GitHub webhook) — not one poll loop per task. On merge → treehouse return and mark the task done. Scales as tasks grow.

7 Scribe /scribe

A knowledge agent you invoke with /scribe. It distills all the agents' learnings and appends only durable, project-intrinsic facts to AGENTS.md — never task-level notes. Same two gates as your memory rule: non-obvious + changes future action. Since AGENTS.md auto-loads for every agent, each one starts smarter.

The quality gauntlet (in order)

Any failure sends work back to the worker, then re-enters the diff review. Nothing ships until every gate is green.

  • Diff review
  • Goal: pass / fail
  • Tests + orthogonality
  • Lint + autofix
  • Open PR
  • Watch for merge
  • Tear down tree
Orthogonality gate: the change must add behavior without breaking unrelated features — that's the real reason tests run here, not just "does it work".
Never-exit rule: the diff-review ↔ worker loop repeats until the reviewer agrees there are zero issues. Only then does a PR open.

The PR contract

Every PR is built for the reviewer's empathy — easy to read, easy to trust.

The template must carry

  • Title in conventional-commit form — actionable, clear
  • Summary of what was done
  • Description: the what and the why
  • Linked items with GitHub tags (bug / issue / feature)
  • Full list of touched files

Ship criteria

  • Atomic — one coherent change
  • Breaking changes flagged explicitly
  • Explicit steps to reproduce / test
  • CI/CD status green

Why it's shaped this way

No echo chambers

The reviewer is a fresh, ephemeral agent that never saw the worker's reasoning. Otherwise the AI just grades its own homework and rubber-stamps it.

One task per worker, many in parallel

Each worker does exactly one task at a time in its own worktree. The orchestrator fans several different tasks out across the pool at once — that's where the parallelism comes from, safely.

Memory outlives the session

Brief + state dotfile live on disk, so clearing the orchestrator to reclaim context never loses the plan or the task list.

You stay in the loop

Workers are spawned as Claude Code subagents, so they show up as steerable windows under your input box natively (herdr as the multiplexer if you outgrow that). Interrupt any that drifts off-plan.

How we'd build it

from parallel technical research
Substrate: build the orchestrator as an interactive Claude Code CLI session, not as an Agent SDK program. The SDK runs the same model, but headless — no window under your input box to watch and interrupt agents, which is the whole point of the orchestrator seat. Keep the merge-watcher as one dumb external gh-axi poll process so its heartbeat survives clear / compact / backgrounding.
Ground ruleslocked by Phase 0 — non-negotiable in the build
  • Workers never use Claude's isolation: worktree / EnterWorktree. The orchestrator leases with treehouse, spawns a plain worker whose cwd is the leased path, and the worker uses raw git. (Opting into Claude's isolation spawns a rival .claude/worktrees/ tree — proven in Phase 0.)
  • The reviewer is never a fork subagent. A plain (non-fork) subagent starts with clean context and sees only the diff — that's the independence guarantee, proven in Phase 0.
  • The merge-watcher lives outside the session as an external gh-axi process — anything in-session dies on /clear.

Phase 0 — de-risk (throwaway)

Before building anything, prove the two scary unknowns in a scratch repo — an afternoon, no product code:

  • Does a Claude subagent editing in a treehouse-leased worktree collide with Claude's own auto-created .claude/worktrees/? Can it be suppressed? (the #1 risk)
  • Does a fresh subagent's context stay provably clean (reviewer can't see worker chat)?

If the collision can't be suppressed → treehouse and Claude-native worktrees fight, and the whole isolation model needs rethinking. Cheap to find out now, expensive later.

Phase 1 — walking skeleton

  1. .canopy/ with brief.md + state.json + one hand-written tasks/<id>.json
  2. Orchestrator = claude --agent orchestrator (Edit/Write denied), spawns ONE worker subagent with worktree isolation (no treehouse yet)
  3. Spawn ONE fresh reviewer subagent on git diff; loop review → fix (via SendMessage) until zero issues
  4. gh pr create; human merges (no watcher yet)
  5. Exit criteria: brief → PR entirely through subagents, orchestrator never edits, reviewer context provably fresh

Top 3 technical risks

  1. Worktree double-management CLEARED in Phase 0 — collision is opt-in; a plain worker on a leased path is fine. Rule: workers never use Claude's isolation: worktree. See Phase 0 results below.
  2. In-model watchers aren't durable — Monitor stops on backgrounding and dies on /clear. The merge-watcher MUST be an external OS process.
  3. SessionStart re-injection contract PINNED — confirmed: fires on startup·resume·clear·compact, output is hookSpecificOutput.additionalContext (≤10k chars). Shape + redundancy spec'd below.

Full write-ups: docs/research/orchestrator-market-research.md and docs/research/orchestrator-technical-research.md.

The merge-watcher — daemon, or something more elegant?

It must live outside the session (proven: in-session watchers die on /clear). But a hand-babysat daemon isn't the answer — here's the ladder:

✗ Hand-rolled daemon

A long-lived while true; gh…; sleep you launch yourself. Dies on reboot, no supervisor, you babysit it. Avoid.

✓ OS-scheduled tick now

launchd (macOS) / cron runs a tiny gh-axi script every ~60s: check open PRs listed in state.json → for merged ones, treehouse return + mark done. The OS is the supervisor: survives /clear & reboot, self-restarts, nothing to babysit. Stateless between runs.

↗ GitHub webhook at scale

Event-driven, zero polling, many repos / org-wide. Needs a small hosted endpoint. Graduate here when you outgrow the laptop or hit API rate limits.

Recommendation: a launchd/cron tick, not a daemon. Rule of thumb — the tick is fine to a few dozen PRs across a handful of repos; switch to a webhook for always-on org scale. Either way the watcher is stateless: it only reads/writes .canopy/state.json, so it survives anything.
Per project? No — one watcher total. It reads the single state.json, which lists every active task with its {repo, pr, worktree}. So one launchd job covers all tasks across all repos; you don't install it per project. Same for the SessionStart hook — put it in user-level ~/.claude/settings.json once, not in each repo.
How does it wake the orchestrator? It doesn't push — the orchestrator is turn-based. The watcher just keeps state.json truthful. Next time the orchestrator takes a turn (you return to it, or it's mid-loop) it reads state.json, sees status: merged, and tears down. There's no reliable "external process injects a message into a running session" primitive in Claude Code — so for a genuine nudge, the watcher fires an OS notification and you continue the orchestrator. Honest limit, not a magic wake.
Is state.json at the Claude hook level? No. state.json lives in .canopy/ — the orchestration layer's own dir, the source of truth. The hook is configured in .claude/settings.json and merely reads .canopy/state.json to build its digest. Two separate things: .canopy/ = data; .claude/ = the hook that reads it.

State contract — and which layer is the source of truth

Your point: ".canopy is just a redundancy." Exactly — but let's be precise about which layer is authoritative, because that decides everything.

.canopy/ = the source of truth

Durable, unbounded, on disk. Survives /clear, compaction, crash, reboot. The orchestrator reads it at the top of every turn — this is the reliable path that always works.

SessionStart hook = the redundancy

A ≤10k-char digest re-injected automatically on startup·resume·clear·compact, so the model is oriented before its first tool call. If the hook ever changed or failed, nothing breaks — the every-turn read of .canopy/ is the belt to its suspenders.

Running it on any project — not just this one

Canopy ships as a CLI (like treehouse). The heavy setup is installed once at the user level and then applies to every repo; per-project is a one-liner.

canopy setup — once, global

Installs the orchestrator agent, the /yolo & /scribe commands, the SessionStart digest hook, and the launchd merge-watcher into user-level ~/.claude/ + launchd. Applies to all projects automatically.

canopy init — per repo (one-liner)

In any project: creates .canopy/ and ensures treehouse is initialized. That's the only per-project step (could even auto-run on the first task). Then start the orchestrator there.

So to onboard another project: cd other-repo && canopy init → run the orchestrator. Nothing else to wire up.

What /clear and /compact do to your workers

Verified against the Claude Code docs — and it changes how workers should be spawned.

/compact — safe

Only summarizes the orchestrator's own history. Workers are unaffected (their transcripts live in separate files) and their panes persist. This is the routine way to reclaim context.

/clear — destructive to in-session workers

In-session Agent-tool subagents are co-scoped to the parent → killed, panes vanish. Only claude --bg detached sessions survive (supervisor-managed, panes stay in agent view, resumable by id).

Design consequence: workers should be spawned as claude --bg detached sessions (tracked by id in state.json), so a /clear on the orchestrator doesn't kill them and their panes stay navigable. And because state.json + the committed worktree are durable, even a killed worker loses no real work — the orchestrator re-spawns on the same leased worktree to continue. Lean on /compact for routine trimming; treat /clear as rare.

Q5 trade-offs — reviewer scope, and a third option I'd recommend

A · One reviewer does everything

+ Sees diff + test + lint together → better root-cause; one verdict; fewer spawns.

– Big context (can overflow); gates can't run in parallel; a flaky test derails the diff read.

B · One agent per gate

+ Small focused contexts; gates run in parallel (faster); easy to add/drop a gate; clean independence.

– More orchestration; no single agent correlates cross-gate signal; more spawn overhead.

C — DECIDED: the worker runs tests & lint itself. They're deterministic commands, not judgment, and the worker already holds the code context — so no new agent and no context bloat, and it fixes its own red results in place. The only thing that stays an independent agent is the fresh diff reviewer (the judgment). No echo chamber, because running tests/lint isn't self-review.
